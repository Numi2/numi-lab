## What the compact, sparse, no-free-rigid scenario says

The report's closest admitted shape to the score-tool path is `sparse_K65536_no_free_rigid_aliases_on_stride15`: 528,444 prepared nodes, 1,477,728 tetrahedra, 260,835 possible cohesive faces (97,984 starch plus 162,851 HMA), 1,054,876 exterior faces, 527,964 contact-eligible exterior nodes, 12 proxies, 9 scene body slots, one environment, and 15 material states. It keeps the explicit flute/tet mesh.

With compact immutable surface storage, an explicit 131,072 deformable-contact capacity, sparse private rigid-contact K=65,536, and both private scratch aliases, the helper reports:

- Modeled Metal envelope: 6,740,173,734 B.
- Modeled host subtotal: 5,750,613,360 B, consisting of two estimated snapshots/checkpoints plus the duplicate staging/readback reserves.
- Corrected combined total: 10,573,915,974 B (9.849 GiB), before the optional tangent cache.
- Tangent cache: 484,694,784 B; estimated combined total with it is 11,058,610,758 B.

That scenario is not admitted by the current full-contact scope. Its failure is the deformable private arena's node/tet/contact cap, not its sparse rigid private arena. Dense accepted rigid-contact state remains modeled at 1,579,685,376 B. Sparse K bounds the private trial sample/index storage (36,090,192 B), but does not remove that persistent dense accepted history.

There is an important accounting omission in this helper: `estimateScenario` fills node/tet/contact dimensions and snapshot counts but never sets `hostSourceMeshBytes`, `hostCompiledWorldBytes`, or `hostGeneratedMetalBytes` (`cardboard_shipping_allocation_preflight.cpp:44-81`). Thus the exact-topology scenarios emit `host_mesh_and_compile_bytes: 0`; their combined totals are still incomplete for a real run. The probe-side prebuild estimator has coarse host reserves based on 256 B/node + 512 B/tet for source mesh, 128 B/node + 256 B/tet for compiled world, plus 64 MiB generated Metal. Applying that same coarse formula to the exact prepared topology gives 1,404,926,464 B of host mesh/compile reserve. With that addition, the no-free-rigid/compact/sparse/alias case is about 11,978,842,438 B; with tangent cache, 12,463,537,222 B. Moving snapshot stride from 15 to 30 adds 177,327,360 B. Adding the selector-4 RAP estimate (837,073,744 B) leaves a modeled 3,701,930,858 B below the 16 GiB limit, before any unknown allocations or safety margin.

Those figures show a technically plausible budget path without replacing the fluted tetrahedral board, not proof that the complete runtime fits. The 1.405 GB host addition is still a coarse reserve; the current CPU helper has no compiled `World` and does not measure vector capacities or temporary construction peaks. For a defensible pre-allocation report, pass the actual `shippingSourceMeshStorageBytes(mesh)`, `shippingCompiledWorldStorageBytes(compiled.world)`, and generated-metal capacity (or exact equivalent inventory) into each scenario instead of leaving them zero.

## Dominant allocation levers and remaining admission work

- **Deformable slots:** Default 8 per tet means 11,821,824 slots and about 7.377 GB. An explicit 131,072-slot bound uses about 81.8 MB, a 7.295 GB modeled saving. This is an overflow-rejecting capacity, not permission to evict history; the complete workload must prove it stays below the chosen capacity or fail/rollback.
- **Surface map:** The compact immutable map reduces its persistent envelope from about 1.010 GB to 218.6 MB, saving 791 MB. It preserves the full exterior-face set and does not reduce node/tet counts.
- **Rigid private trial samples:** The 6,335,568-node/proxy rows make dense private trial samples about 1.064 GB. Sparse K=65,536 plus the 4P stable-ID map is about 36.1 MB, saving about 1.028 GB for private Armijo work only. Conservative candidate completeness, deterministic canonical IDs, and unchanged accepted-history identity remain required. The dense persistent pair/history arrays (about 1.580 GB) remain in this model.
- **Scratch aliases:** Reusing self-surface and cohesive scratch reduces only the exclusive full-contact trial workspace; it does not shrink persistent face/state counts or bypass their scope checks. The all-interface case still exceeds the current 4,096 cohesive-face admission cap and private FEM node/tet caps.
- **Rigid degrees of freedom:** The report's `sparse_K65536_six_free_rigid_aliases_on_stride15` is a rejected sensitivity, not a qualified free-box path. Its shared admission call rejects free rigid unknowns for this 12-proxy/9-body layout. The lower-memory continuation for scoring is prescribed/static tooling (`rigidGeneralizedCapacity=0`), with the FEM box remaining the explicit deformable solid. A one-free-BOX path would need a source-authored proxy-layout check and production parity before using sparse private trials.
- **RAP:** Selector 2 is estimated at 456,581,968 B; selector 4 at 837,073,744 B, both above the current 256 MiB cap. They can fit in the coarse additive budget above, but the actual checked buffers, environment multiplier, GPU workgroup limits, and a source-bound runtime observation still need validation before changing admission.
- **Count gates:** The current world exceeds the 8,192-node and 32,768-tet full-contact limits; the combined cohesive count (if both interface laws are enabled) exceeds 4,096. The next implementation should replace those fixed thresholds with checked 64-bit buffer/index sizing and explicit whole-runtime budget admission, while streaming/aliasing private face work and preserving complete candidate/history coverage. Raising the constants alone would not be safe.

A feasible staged path is therefore: retain the exact explicit flute/tet geometry and source constituent regions; use the compact face map; run with prescribed tooling and an explicit deformable-contact capacity that rejects atomically on overflow; keep sparse private contact opt-in and parity-checked; then replace node/tet/cohesive count caps with checked allocation/index/workgroup admission and exact temporary-memory lifetimes. Do not call this path admitted until the helper counts actual host vectors, the relevant capacities/scope checks pass, and a native initialization reports runtime resident/currentAllocatedSize plus host footprint. Those observed counters continue to be compared by maximum because they can overlap on unified memory; the modeled allocation inventory is additive.
