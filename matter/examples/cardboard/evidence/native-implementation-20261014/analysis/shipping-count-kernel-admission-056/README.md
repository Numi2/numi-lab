## Actual ABI/index assumptions and hidden work

`NMMatterDispatchGPU` stores environment, node, tetrahedron, rigid proxy, pair, surface, cohesive, and contact capacities as 32-bit fields (`shared.h:350-410`). The FEM contact compiler checks N-capacity times proxy count against uint32 before cooking (`compiler_impl.cpp:3044-3064`); topology tet capacity is checked before storing (`compiler_impl.cpp:3502-3514`). Metal FEM/cohesive kernels form `environmentCount * tetrahedronCount` or `environmentCount * cohesiveFaceCount` in `uint` (examples `fem.metalinc:1004,1775,2103,2454,2606,2795,2914,3627,4432`). Surface/contact kernels similarly multiply E by primitive, pair, or K strides (`contact.metalinc:1945,1970,2073,2096-2097,2137-2147`). The sparse admission helper explicitly proves E*P and E*K fit uint32. Any larger-count path needs an explicit product proof before dispatch, even when each individual count fits.

No uint16 tet/node/pair identifiers or per-element local arrays scaling with the full shipping count were found in the inspected path. The meaningful current blockers are source/runtime scope and checked arena budgets, plus uint32 flattened domains and address calculations. Metal dispatch currently computes threadgroup widths from pipeline limits and uses `NSUInteger` launch counts in the runtime; the source audit does not establish a device-specific maximum grid size or max buffer length for every scratch buffer. Runtime allocations can still fail on nil Metal buffers; only the tangent-cache path has an explicit `device.maxBufferLength` check (`runtime.mm:5144-5158`). Device-bound allocation and launch tests remain necessary before any admission claim.

## Memory envelope and smallest safe next step

The 16 GiB ceiling is enforced by the cardboard preflight model, not a universal runtime allocator cap (`cardboard_shipping_memory.hpp:27` and host/metal overlap accounting in the same file). Source-55 modeled peak values use a previous 453,378-node / 1,477,728-tet base runtime resident anchor and add explicit surface, contact, cohesive, tangent, regional, snapshot, and host overlap terms. Those scenario totals are estimates, not a full-world source-56 Metal peak; `whole_process_preallocation_admission.complete=false` and `metal_runtime_initialized=false` in the retained source-55 JSON are decisive limits. Two retained full checkpoints and upload/readback overlap are represented in the CPU model; they are not actual allocated buffers in this audit.

Smallest safe first extension is not to lift N/T/C caps. It is to add a shared checked allocation-plan admission for a *bounded* topology slice: prove every `E*count`, BVH `4*bit_ceil(primitiveCount)`, K/P map, cohesive-copy, and bytes-per-arena multiplication; compute the simultaneously live runtime plus snapshot/host buffers; compare each Metal buffer against device `maxBufferLength`; then run an exact-count native initialization and one no-motion accepted transaction with unchanged status/certificate/overflow rollback. The full shipping mesh is outside current full-contact FGMRES source/compiler/runtime scope regardless of rigid sparse savings. A productive path must first widen/stream a single well-defined arena with all callers and rollback lifetimes accounted for, rather than just raising the current fixed caps.

The probe update in this source-56 working tree now reads self-contact flags from the compiled FEM object, exact sparse capacity/parity parsing, surface/cohesive scratch-alias requests, and the bounded free-BOX predicate. It accepts P>65,536 in shipping residual-descent admission only when sparse private contact is requested; the shared allocator/helper still performs the canonical uint32, free-body layout, and 36 MiB checks. On any invalid runtime configuration, private scratch alias savings are removed from the estimate so a rejected request cannot understate arena bytes. Prebuild estimation remains dense/conservative. This change is a CPU preflight mirror only; it does not change solver caps or claim shipping admission.
