# PX4 X500 native flight foundation

The bundled `px4_x500` RobotPack is pinned to PX4 Gazebo Models revision
`e00d3b9cde682dbcb3bf6f30a2f2b8ef4325dae8`. Source acquisition utilities
verify that revision and its file hashes; production simulation enters through
the same `RunManifest -> CompiledRun -> MetalWorld` executor as G1 and Franka.

The runtime is data-driven. `MRMulticopterModelGPU` and rotor records are
generic fixed-layout inputs. Four typed `rotorMixer` actuator lanes read the
filtered TaskProgram action history, advance transactional persistent
motor-speed state, and write one body wrench per environment. The ordinary ABA
step then applies that wrench together with gravity; ordinary MetalWorld
collision/contact handles the authored X500 shapes and ground. No airframe
branch, host per-environment controller, alternate integrator, or gravity
bypass exists.

The current X500 configuration is sourced from the pinned SDF: the base and
four rotor-link masses are reduced into one COM-centred rigid airframe, rotor
poses are expressed from that composite COM, and motor rise/fall constants,
maximum speed, thrust coefficient, moment constant, rotor drag, and rolling
moment coefficient are retained. The CPU FP64 actuator oracle and Metal wrench
kernel must agree before the flight probe accepts a run.

The unified CompiledRun qualification executes 256 environments for 104 control
steps (26,624 environment steps) on Apple M4 with zero failed steps. The neutral
run retained height in `[1.91696, 2.07746]` m and maximum tilt `0.0479346` rad.
This is native GPU simulation evidence only. It does not
yet qualify a real X500, wind-tunnel aerodynamics, rotor angular-momentum
coupling, sensor fusion, controller tracking, collision/CCD in flight, or
hardware safety. Those require pinned external comparisons and then separately
armed physical-flight evidence.

## Native policy task contract

The PX4 RobotPack declares four canonical policy actuators: collective, roll,
pitch, and yaw. Each lane is clipped to `[-1, 1]`; collective changes all rotor
speed targets, roll/pitch use source attachment signs, and yaw uses source
reaction-torque signs. SensorPack publishes local linear/angular velocity,
projected gravity, root height, and previous actions. TaskPack publishes the
same generic learner transition and typed outcome ABI used by other robots:
the five universal transaction outcomes plus root height, tilt, and tracking.

The executable probe uses only the public CompiledRun boundary:

```sh
build/bin/metalrobo_px4_x500_gpu_probe \
  build/shaders/MetalRobo.metallib 256 104
```

Motor state, robot state, contact state, task state, sensor history, and reset
state are all transactional resident state. A failed environment rolls back
without publishing a partial motor or physics update. No learned X500 policy
is claimed by this qualification.

## Physics maneuver replay

`numi drone maneuvers --trace <file>` records a six-second, conservative
closed-loop policy-format reference: ascent, lateral bank, lateral recovery,
yaw input, and descent. It reads the accepted body state only to choose the
next four action lanes; each state in the trace is still advanced by the
native Metal mixer, rotor model, wrench, and free-body integrator. The helper
is a deterministic rendering/reference controller, not a learned policy.

```sh
numi drone maneuvers --trace .numi/runs/px4-x500-maneuvers.csv
blender --background --python tools/render_px4_x500_flight.py -- \
  --trace .numi/runs/px4-x500-maneuvers.csv \
  --source-root .numi/runs/px4-x500-source/source \
  --frames .numi/runs/px4-x500-render/maneuver-frames \
  --sample-stride 21 --world-camera
```

The fixed-camera mode follows no drone transform, so altitude, translation,
and attitude in the render are directly visible. It remains simulator output,
not real-flight evidence.

## Torque-driven roll replay

`numi drone roll --trace <file>` records one closed-loop, full-roll reference
from an elevated spawn. The helper accelerates and brakes against the accepted
unwrapped body rotation and angular velocity, then sends the same four policy
lanes through the Metal mixer and persistent motor dynamics. The trace includes
`roll_travel_rad`, integrated from each accepted orientation, so the reported
turn is independently inspectable rather than inferred from a render. The run
rejects traces that never invert or do not settle within 0.10 rad of one turn.

```sh
numi drone roll --trace .numi/runs/px4-x500-roll.csv
blender --background --python tools/render_px4_x500_flight.py -- \\
  --trace .numi/runs/px4-x500-roll.csv \\
  --source-root .numi/runs/px4-x500-source/source \\
  --frames .numi/runs/px4-x500-roll-render/frames \\
  --sample-stride 4 --tracking-camera
```

`--tracking-camera` follows only accepted position and never the airframe's
orientation, so the body rotation remains visible throughout the roll.

This is an acrobatic simulator trajectory, not a hover-task episode or a
learned policy evaluation; the hover task is intentionally not evaluated while
the airframe exceeds its attitude termination limit. It also does not qualify
real X500 flip behavior: rotor angular-momentum coupling and externally
validated acrobatic aerodynamics are not yet modelled.

### Rotor visual provenance

Maneuver traces retain all four accepted `rotor*_rad_s` values alongside body
pose and policy action. The renderer integrates those exact speeds into blade
angles. Its spin roots are the source `rotor_N_joint` origins (each has SDF
axis `0 0 1`), while the propeller mesh retains its authored visual offset and
scale beneath that joint. Turning direction is read from the pinned X500 SDF:
rotors 0/1 are CCW and 2/3 are CW. The renderer deliberately applies no
artificial rotor or airframe motion blur.

## Render an accepted Metal flight trace

The flight probe can additionally emit one accepted X500 body-state trace from
the same native Metal kernels. Render it with the original PX4 X500
presentation geometry (carbon frame, landing gear, motor bells, and propellers):

```sh
numi drone source --output .numi/runs/px4-x500-source
numi drone flight --trace .numi/runs/px4-x500-flight.csv
blender --background --python tools/render_px4_x500_flight.py -- \
  --trace .numi/runs/px4-x500-flight.csv \
  --source-root .numi/runs/px4-x500-source/source \
  --frames .numi/runs/px4-x500-render/frames \
  --sample-stride 7
ffmpeg -framerate 24 -start_number 1 \
  -i .numi/runs/px4-x500-render/frames/x500-%04d.png \
  -loop 0 .numi/runs/px4-x500-render/px4-x500-metal-ascent.gif
```

The renderer follows recorded poses; `--sample-stride` selects accepted states
for presentation and does not synthesize a trajectory. It is a visualisation
of simulation output, not evidence of visual-airframe fidelity or real-world
flight.
