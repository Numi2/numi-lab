# Preregistered changing-depth frame restoration diagnostic

The previous 50 Hz study changed camera metadata but not depth, identity or validity pixels. In this separate study the sixth, visible target starts with a -1 m/s world-z velocity in both environments and both arms. With no scene-velocity randomizer or impact hold in this test task, the target is expected to approach the upward-facing camera by roughly 0.02 m per 20 ms step, in addition to gravity. The five-sphere overflow trigger, target position and all other geometry, policy, reset behavior, 50 Hz cadence and single-step research implementation remain fixed. Actual motion, visibility, pixel change and failure are hypotheses; later published scene readback is reported with its previously stated limitations.

Run a no-candidate baseline, candidate with frame snapshots, and candidate without frame snapshots, each once with 120-second timeout. Retain exact task/policy/binary/shader/asset identities, all status, depth/identity/validity/camera/track bits, actor histories, device clocks, and times. Require two accepted visible target frames, the genuine mixed raw-contact failure on step 3, and successful control. Baseline environment 0 must have at least one target pixel with a changed depth bit between accepted step 2 and rejected step 3; if so, compare exact candidate failed-environment step-3 depth and other sensor states against its own step-2 state and compare successful environment 1 against the baseline and its control. Confirm device clocks (2,1) and (3,2), and report any mismatches. If an ID or validity bit never changes in the baseline, its restoration is not qualified. Compare candidate and no-snapshot output at printed precision.

The GPU clocks are accounting state and do not drive per-environment renderer scheduling; the mode refuses a further step after divergence. No retry, automatic-reset continuation, masked-depth history, multi-step command buffer, or production qualification follows.
