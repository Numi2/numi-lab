# Single-step host candidate publication feasibility

This is a research-only host observation-publication projection, not a production sensor transaction. It stages each environment actor-observation vector against a source generation. It refuses absent command completion, absent validated publication, stale generation, stale attempt tokens and malformed dimensions. Each attempt is uniquely numbered and consumed even on failure; the synchronous single-threaded owner permits only one in flight. The helper has no locking or asynchronous callback lifetime guarantee. It constructs a new host vector first and replaces only environments for which both validated world and contact statuses are success. Rejected environments retain their explicitly initialized sentinel record; the record is not claimed to be a real previously accepted frame. Its small CPU test covers rejected certificates, stale callbacks after an all-failed attempt, overlapping candidates, malformed sizes, mixed statuses and all-failed statuses.

The native fixture uses the isolated pre-submit guard owner and a Franka pick-place task with two environments, a direct-winner synthetic visual pack and zero policy. A test hook induces an actual pre-submit refusal first; absence of a completed validated result must leave the host publication at generation 0. The next single-step uses the real MetalWorldSubmission wait and publishes a candidate only after its own diagnostics report a completed validated result with two correctly indexed world and contact statuses. The positive command-completion condition is certified by the implementation path: diagnostics.published is set only after wait has observed MTLCommandBufferStatusCompleted and validateAndPublish has succeeded. An error return alone or zero-initialized status arrays is not sufficient.

The two arms are separately initialized with identical task contract and capacity one. Both environments in control keep the two dynamic boxes far from robot and ground; in the mixed arm only environment 0 places both boxes in the same location at the ground. The intended genuine raw-contact overflow in environment 0, successful environment 1 and successful control are hypotheses, not guaranteed. Both arms require the direct-winner path and two valid physical status records. Retain every status and required contact count. Stop on failed prerequisites; an all-fail, no-fail, compilation or capacity failure is inconclusive for mixed publication. Only if the mixed prerequisite passes require rejected env 0 sentinel and accepted env 1 candidate, and compare env 1 candidate actor bytes against independent control.

Run CPU unit test first, then one native process for control and, only after it succeeds, one for mixed; each native process has a 120-second timeout, pinned identities and pre/post input hashes. No retries. Preserve all failed arms and outputs.

This projection is intentionally not a production solution: the resident task, physics, tracker, frame buffers and cadence may already have mutated, and the first rejected-environment sentinel is not a retained accepted frame. No GPU command failure is induced. No automatic-reset, per-environment retry, nonempty visual, actor-history, physical camera, policy fingerprint, multi-step, or transactionality claim follows. A true owner-level candidate arena and completion-owned commit remain necessary.
