# Direct-winner completion and publication boundary

This is a source trace, not a new native test. The tested asset and admission results are in RESULT.md; statuses there were injected by the fixture.

The visual observation program in include/metalrobo/MetalWorld.hpp borrows its command buffer and other buffers for encoding and explicitly cannot retain, submit or wait for them. MetalWorld.mm encodes native task observation, the device visual callback, policy action and physics in one command buffer, potentially for multiple control steps, then submits it. MetalHybridObjectTracker::encodeObservation uses a host cadence candidate, encodes the render and observation, and commits that cadence immediately after successful encoding. This is not a capture completion certificate. Renderer activeMetadata is assigned on the host during encoding and is batch-shared; it is not a per-environment completed-frame status.

MetalWorldSubmission::wait learns whole-command completion only after waiting, before copying results and validating/publicizing them. Its submission state destructor also waits and finalizes resident buffer selection according to command completion and arena ownership. The visual callback carries a raw context pointer and has no completion or abort callback, owned submission token, or lifetime guarantee extending through that completion boundary. FRAME validity is a per-pixel shader result: it does not certify command completion, and the direct-winner path does not materialize the same validity plane. Neither empty winners nor camera pose validity establishes a missing frame.

A safe real producer must be introduced by the actual capture and submission owner, not inferred from the rendered pixels. In the current in-command renderer a device marker emitted after rendering can show which environment was encoded and reached that point, but a marker is provisional until the owning command completes successfully. A successfully rendered empty scene is then present; a failed command cannot publish any marker or candidate output. A physical rejection is a separate per-environment outcome and requires its own acceptance signal. Per-environment held frame, tracker, actor history, metadata and cadence must remain candidate state until the matching acceptance outcome; command failure must preserve the prior accepted state even after partial GPU writes.

The smallest credible next implementation needs submission-owned lifetime and completion/abort handling for the observation transaction, candidate buffers distinct from accepted buffers, and a defined per-step status/commit order. Multi-control-step submissions need device-visible sequencing between steps or a bounded single-step mode with a completion boundary. If command completion or validation fails, no host cadence or candidate pointer may advance; mixed physics results must only commit their accepted environments. Existing automatic reset semantics and explicitly separate no-reset retry behavior must both be specified and tested. A simple callback to the raw tracker in the current submission destructor is insufficient: tracker lifetime is not owned there, cadence already commits during encoding, buffer contents may have been partially written, and command completion alone does not certify per-environment physics acceptance or successful result publication.

Tests should include real completed empty and nonempty frames, an actual capture/command failure, mixed accepted and rejected physics, exact private state and held pixels, continuation and automatic reset, plus dropped or unconsumed submission lifetime. The existing injected-status fixture verifies admission plumbing only. Observation fingerprint migration, old-policy rejection, renderer cadence divergence, and resident retry remain separate qualification gates. No production boundary or fingerprint was changed by this report.
