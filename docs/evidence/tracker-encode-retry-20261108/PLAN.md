# Tracker encode failure and immediate retry

Question: does a rejected visual tracker encode advance the next sensor sequence before any command is submitted? Use the real main-owner Franka visual-platform probe and renderer, two environments, fixed scene and default 50 Hz sensor/control cadence. Extend the existing fixture with an opt-in first encode using an invalid body count, in a separate command buffer which is never committed. Require that attempt to return false, the prior renderer frame metadata to stay unchanged, and the subsequent valid command to complete with sensor sequence zero, identical to an otherwise matched no-fault process. Existing visible geometry, depth/history, task and finiteness gates remain active. The baseline is expected to advance to sequence one in the fault arm; the no-fault arm must report zero. The candidate must pass both arms. Bind executable, dylib, metallib and source hashes and keep the first failing result. Run one process per arm and retain all exits, metadata and native output.

Only after reproducing the defect, examine a production change that makes the tracker callback's own validation/encoding failure leave its host cadence, renderer metadata and render uniforms unchanged. Do not claim this covers failures later in MetalWorld submission, GPU command errors, mixed physical acceptance, private-buffer rollback or retry after physical failure. Those require a completion-owned transaction and per-environment state. Keep contact and CCD options unchanged.
