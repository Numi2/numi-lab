# Preregistered owner observation and status-gated metadata slice

This isolated single-step research owner connects the previously tested mixed-frame candidate method to the real observation callback, but only after two accepted nonterminal steps and while the per-environment clocks are synchronized. The ordinary owner path remains unchanged unless explicitly configured; the existing outer divergence guard remains active. The callback renders candidate frame slices with each environment's accepted sequence and places separately generated candidate metadata in shared research buffers. The existing status-gated finish hook restores rejected actor, tracker and depth/ID/validity/camera slices; a test-only GPU selector commits candidate per-environment metadata and clock records only for successful world/contact statuses. The renderer's ordinary shared metadata is still speculative and must not be used as accepted per-environment metadata.

Use the existing 25 Hz, 20 ms, 5 mm depth-noise moving-target fixture. Require two accepted nonterminal steps and then the real env-0 overflow / env-1 success. Step 3's actual proposed frames for both synchronized clocks are frame/sensor 2/1 at approximately 0.04 s. The failed environment must retain all prior frame, tracker, actor, clock and accepted-metadata words; the successful environment must match a separate actual renderer reference generated from its captured observation-time body state, and commit the reference metadata and clock. Retain exact words and count changes so unchanged fields are not treated as challenged. Attempt one subsequent submission and require the existing outer guard to refuse it before observation; compare the retained visual snapshots across refusal. A separate fresh/no-snapshot control is not part of this gate.

Run once with a 120-second timeout, capture all outputs and verify pinned binaries, shaders and assets before and after. Initial compile failures and corrected builds are retained. This is an opt-in synchronized candidate inside one actual mixed-success step; it does not permit or test differing sample phases on a live step, automatic-reset continuation, physical retry, masked-depth history, multi-step submissions, device-command failure or non-oracle deployment. The guard must not be removed on the basis of this result.
