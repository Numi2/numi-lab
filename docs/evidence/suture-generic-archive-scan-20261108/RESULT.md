# Generic branch-tip archive member search

The continuation searched member names in the 282 distinct tracked archive-like blobs left outside the previous 18 fresh-approach archives, using the same frozen 119 branch heads. Of the 282, 270 ordinary tar archives were listed successfully, three zstd archives were listed in the separately planned pass, and nine were symbolic-link blobs rather than archives. For each link, the frozen tree entry has mode 120000; in one referenced frozen tree its target was tracked and was one of the 270 successfully listed archives. The primary scanner's nine truncated-header failures are retained rather than silently recategorized, and the zstd primary-pass omissions are retained alongside the successful supplemental pass.

The 273 successfully listed archives contain 26,207 member entries and 109 matches for the declared broad name pattern, in six archives. The matches were source files and headers, including suture-related program source; none identifies a tissue-receiver-bridge-start state or receipt by name. No candidate earned checkpoint was established. This result does **not** contradict the user's branch location: a checkpoint may have a generic member name, be nested in an archive or object pack, live in an older commit tree, or exist outside this frozen tip inventory. Archive member names and byte counts do not establish the contents, stage, complete coupled owner state, or native replay. In particular the zstd object-cache archives' nested Git objects were not searched as Git repositories. This was a member-name listing, not a full archive integrity or payload audit.

All 273 archive streams and the nine retained errors reproduced byte-for-byte on a second read with the same scanner; per-object compressed-byte SHA-256, byte count, member counts, selected names, and exit status are retained. `link-analysis.json` identifies the specific frozen ref and tree used for each link resolution. The scan used local Git objects with lazy fetching disabled, did not extract an archive, and did not modify, restore, or substitute any checkpoint. No timing or performance claim is made.

The next search should inspect older surgical branch trees and candidate generically named checkpoint metadata under explicit byte and resource limits. A real candidate must then pass stage, provenance, state-ownership completeness and native replay checks before advancing the tissue-coupled workflow. The `inventory.json` is the exact inventory previously retained in `docs/evidence/suture-branch-tip-search-20261108`; the frozen refs and source of its objects are recorded there. Plans, scanners, raw JSONL and supplemental zstd output are included here. `repeat-sha256.txt` binds both repeated result files; the repeat output compared equal before this report was written.
